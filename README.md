# TraceGuard

> FFT 기반 이미지 워터마킹을 활용한 기업 기밀문서 유출 경로 역추적 플랫폼

- **분야**: AI · 정보보안 · 기업용 SaaS
- **핵심 기술**: Digital Watermarking, FFT, Document Traceability, Graph-based Tracking
- **대상**: 제조업 · 반도체 · 기술개발 기업 등 외부 협력사와 기밀자료를 공유하는 기업

**"유출된 문서가 어디에서 왔는지, 어떤 경로로 전달되었는지 확인한다."**

---

## 1. 문제 정의

- 기밀자료는 직원 → 협력사 → 외부 파트너로 **여러 단계에 걸쳐 공유**된다 (예: 원본 기업 A → 직원 B → 협력사 C)
- 외부에서 유출본이 발견되면 "자사 문서"인 것은 알아도 **어느 배포 사본에서, 어느 단계를 거쳐** 나갔는지는 따로 조사해야 한다
- 기존 식별 방식의 한계
  - 파일명 · 메타데이터: 쉽게 변경 · 제거됨
  - 파일 해시: 내용이 조금만 바뀌어도 달라짐
  - 캡처 · 촬영: 파일에 붙은 식별 정보가 사라짐
  - 배포 기록이 여러 시스템에 흩어져 있어 유출본과 배포 관계를 잇는 데 추가 조사가 필요함

## 2. 해결 방안

두 기술을 결합한다.

### 2.1. FFT 기반 이미지 워터마크
- 이미지를 주파수 영역으로 변환해 **사본별 고유 식별 정보**를 삽입
- 같은 문서라도 배포 대상마다 다른 사본 생성
  - 원본 `DOC-A001` / 직원 B `COPY-B102` / 협력사 C `COPY-C203`
- 유출본에서 워터마크를 검출해 어떤 배포 사본인지 식별
- 검출 성공 여부는 알고리즘과 변형 정도(압축 · 크기 변경 · 촬영)에 따라 달라짐 — 모든 상황을 보장하지 않음

### 2.2. 문서 배포 계보 역추적
- 사본 발급 시마다 기록: 원본 문서 ID, 새 사본 ID, **부모 사본 ID**, 배포 대상 · 배포자, 배포 일시
- 기록: `DOC-A001 → COPY-B102 → COPY-C203`
- 유출본에서 `COPY-C203` 검출 시 부모를 거슬러 조회: `COPY-C203 → COPY-B102 → DOC-A001`
- 한 문서가 여러 대상에게 나뉘어 배포되는 **분기**도 저장
- **기록되지 않은 이동 경로는 복원하지 않는다.** 실제 유출 행위 · 책임은 별도 증거로 판단

### 2.3. 분석 흐름
```
① 유출 이미지 등록 → ② 워터마크 분석 → ③ 배포 사본 식별 → ④ 배포 계보 복원 → ⑤ 결과 시각화
   (보안 담당자 업로드)  (주파수 성분 분석)   (사본 DB 대조)      (부모 관계 역조회)    (그래프 · 보고서)
```

## 3. 핵심 기능

| 기능 | 내용 |
|---|---|
| 문서 등록 · 사본 관리 | 문서에 고유 ID 부여, 배포 대상별 워터마크 사본 생성, 원본 · 부모 사본과 연결 |
| 워터마크 삽입 · 검출 | 사본에 식별 정보 삽입, 검사 이미지에서 검출 (메타데이터가 바뀌어도 시도 가능) |
| 유출 이미지 자동 분석 | 업로드 → 파일 검증 · 워터마크 검출 · 배포 기록 조회를 단계별로 안내, 실패 · 기록 없음도 명확히 안내 |
| 배포 계보 시각화 | 식별된 사본 기준으로 원본까지 그래프 표시, 노드 선택 시 배포 대상 · 일시 · 사본 ID 확인 |
| 조사 결과 관리 | 사건별 관리, 보고서(유출 이미지 · 식별 사본 · 계보 · 활용 기록 · 추가 확인 사항) |

## 4. 시스템 구조

```
[프론트엔드] ──▶ [백엔드: 데이터 관리 · 추적] ──▶ [이미지 분석 엔진]
 문서 등록           문서 · 사본 · 부모 관계 저장        FFT 워터마크 삽입 · 검출
 유출 분석           사본 → 원본 계보 역조회              식별 정보 복원
 계보 그래프 · 보고서
```

| 영역 | 역할 |
|---|---|
| 프론트엔드 | 문서 등록, 유출 의심 파일 분석, 배포 계보 확인 웹 UI |
| 이미지 분석 엔진 | FFT 기반 워터마크 삽입 · 검출, 식별 정보 분석 |
| 데이터 관리 · 추적 | 원본 · 사본 관계 저장, 식별된 사본에서 최초 원본까지 경로 조회 |

- **역추적 알고리즘**: 검출된 사본의 부모 ID를 최초 문서에 닿을 때까지 반복 조회
- **분기 지원**: 한 사본에서 여러 자식 사본이 나오는 트리 구조로 저장

## 5. UI/UX

- 작업 중심의 단계적 화면 — 필요한 정보만 순서대로 제공
- **업로드**: 중앙 업로드 영역 → 미리보기 · 파일 정보 확인 → 분석 시작
- **분석 진행**: 파일 처리 → 워터마크 검출 → 배포 기록 조회 상태 표시
- **결과**: 사본 ID · 원본 문서 · 계보 요약, 기술 수치는 상세 보기로 분리
- **배포 경로**: 그래프 시각화, 노드 선택 시 사본 정보 표시

## 6. 차별화

새 변환 기술의 발명이 아니라, 기존 기술(FFT 워터마킹 · 문서 식별 · 배포 이력)을 **"유출 이미지 → 사본 식별 → 다단계 계보 확인"** 하나의 흐름으로 연결하는 데 초점을 둔다.

1. 원본 식별을 넘어 **사본별 중간 배포 관계**까지 추적
2. 파일명 · 메타데이터가 아닌 **이미지 픽셀 속 워터마크** 활용
3. 결과를 **직관적인 그래프**로 제공
4. **검증된 정보와 추정 정보를 구분** — 기록으로 확인된 관계만 확정으로 표시

## 7. 성능 검증 계획

| 항목 | 평가 내용 |
|---|---|
| 워터마크 검출 | 정상 이미지에서 식별 정보를 정확히 검출하는가 |
| 이미지 변형 대응 | JPEG 압축 · 크기 변경 후에도 검출되는가 |
| 이미지 품질 | 삽입 전후 시각적 품질 차이 (PSNR · SSIM) |
| 오탐률 | 다른 사본의 식별 정보로 잘못 검출하지 않는가 |
| 배포 경로 복원 | 등록된 부모-자식 관계를 정확히 조회하는가 |
| 처리 시간 | 업로드부터 결과 표시까지 소요 시간 |

## 8. 한계

- 관리 시스템 **밖에서 이뤄진 전송은 추적할 수 없다** (기록된 배포 이력 기준)
- 워터마크만으로 **실제 유출자를 확정할 수 없다** — 초기 조사 단서 제공이 목적
- 압축 · 크기 변경 · 촬영 · 잘라내기 등 모든 변형에서 검출을 보장하지 않는다

## 9. 기대효과

- **초기 조사 효율 개선**: 검출 → 계보 조회 자동화로 관련 문서 탐색 · 전달 관계 확인 업무 감소
- **협력사 자료 공유 관리**: 사본별 배포 대상 기록, 다단계 협업에서 배포 범위 확인
- **이미지 기반 기술자료 보호**: 반도체 설계도, 제품 렌더링, R&D 이미지, 미공개 디자인 시안
- **조사 결과 가시성**: 보안 담당자 · 관리자 모두 전달 구조를 이해

## 10. 사업화 · 확장

- **목표 고객**: 기술자료를 외부와 공유하지만 전문 추적 시스템 구축이 어려운 중소 · 중견 기술기업
- **수익 모델 (검토)**: 기업용 SaaS 구독
  - 기본: 문서 등록, 사본 발급, 유출 이미지 검사, 배포 이력 조회
  - 상위: 문서량 확대, 협력사 관리, 고급 분석, 보고서, 외부 시스템 연동
  - 가격 · 과금 기준은 고객 인터뷰 · 도입 비용 분석으로 검증 필요
- **확장 방향**
  - PDF 등 다양한 파일 형식 지원
  - 압축 · 크기 변경 · 촬영 · 잘라내기에 대한 워터마크 강건성 향상
  - 기존 문서관리 시스템 연동으로 배포 정보 자동 기록
  - 증거 자동 정리, 기록 누락 · 추가 확인 필요 구간 안내

## 11. 결론

TraceGuard는 **FFT 기반 이미지 워터마크 검출**과 **다단계 문서 배포 계보 역추적**을 결합해, 유출 이미지에서 식별한 사본을 출발점으로 기록된 전달 관계를 조회하고 이해하기 쉽게 시각화한다. 모든 이동을 추적하거나 유출자를 확정하지는 않지만, 관리된 배포 과정의 증거를 연결해 유출 사고 초기 조사에 필요한 단서를 제공한다.

## 12. 레포 구조

```
.
├── frontend/     프론트엔드 (예정) — backend /api 만 호출
├── backend/      자바 웹 (Spring Boot, :8080) — 수신자 대장 · 검출 이력 · API
├── tracing/      .hck 파일 유출 경로 역추적 (Python FastAPI :8001 + React :5173)
├── watermark/    휴대폰 촬영본 워터마크 추출 엔진 (Python Flask, :8000)
├── docker-compose.yml   MySQL + backend
└── .env.example
```

```
[frontend] ──/api──▶ [backend :8080] ──/v1──▶ [watermark :8000]
                                        (예정)─▶ [tracing   :8001]
```

| 폴더 | 추적 대상 | 문서 |
|---|---|---|
| `backend/` | — | `./gradlew build` (backend/ 에서) |
| `tracing/` | 파일 그대로 전달된 경로 (A→B→C→D) | [tracing/README.md](tracing/README.md) |
| `watermark/` | 화면을 촬영해 이미지가 된 유출본의 유출자 | [watermark/API.md](watermark/API.md) |

## 13. 실행

```bash
docker compose up -d --build                                    # MySQL + backend (로컬 3306 사용 중이면 MYSQL_PORT=3307)

python -m venv .venv
.venv/bin/pip install -r watermark/requirements.txt -r tracing/server/requirements.txt
cd watermark && WM_KEY=<비밀키> ../.venv/bin/python server.py   # :8000
cd tracing/server && ../../.venv/bin/uvicorn main:app --port 8001
```
